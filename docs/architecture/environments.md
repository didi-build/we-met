Four environments share one codebase. **Production** and **PR previews** use Worker name **`we-met`** (production bindings at the top level of Wrangler config, **non-prod bindings** in the **`previews`** block; previews do not inherit production settings). **Staging** uses a separate Worker **`we-met-staging`** on `we-met.didi.build` with the same non-prod resource names as previews ([0028](../decisions/0028-staging-we-met-didi-build.md)). **Non-prod never uses the production queue, consumer, rate limiter namespace, D1 database, or R2 bucket.**

## Non-prod mail safety

Preview, **staging**, and local (remote) share **one** non-prod queue and consumer (`we-met-followup-email-consumer-nonprod`). The redirect to `WE_MET_TEST_MAIL_TO` is **hardwired in the non-prod consumer’s own config**, not read from queue messages. It **fails closed**: if the test address is unset, **nothing is sent**. The delivered message still shows the **address the visitor typed** in the subject or body. Staging outbound mail is stamped as test mail per [0028](../decisions/0028-staging-we-met-didi-build.md).

## Previews

PR previews are served on **workers.dev** (`<preview-name>-we-met.<subdomain>.workers.dev`) and via Cloudflare **Previews**. **Version URLs** reuse the Worker’s own resources; Cloudflare advises against them for PR testing. **Previews isolate per PR.**

PR previews deploy via a **GitHub Actions** workflow that runs `wrangler preview` ([0019](../decisions/0019-pr-preview-github-action.md)). **Forks never get deploy access.** Secrets are set once in the **Previews base configuration** and apply to every new preview (per Cloudflare docs; not yet verified here, see [deploy-setup.md](../runbooks/deploy-setup.md#worker-secrets)). A preview is **deleted when its PR closes**. Previews may **produce** to queues but **cannot consume** them; the non-prod consumer is a **separate Worker**. Requires **Wrangler 4.135.0+**.

**`WE_MET_BASE_URL` in the `previews` block is `https://we-met.link`**, so links in test emails, the vCard URL field, and canonical/OG URLs from a preview point at production card pages, not the preview hostname. The preview hostname still serves the card via lookup configuration. Until [DIDI-882](https://linear.app/didi-build/issue/DIDI-882), the non-prod consumer uses the same production origin in `wrangler.nonprod.jsonc`, so **staging** test mail links behave like previews even though the staging app Worker will use `https://we-met.didi.build`.

Preview deployments receive **ASSETS**, **IMAGES** (when `previews.images` is set), **WE_MET_ASSETS**, **WE_MET_BASE_URL**, **WE_MET_DB** (non-prod D1), **WE_MET_ENV** = `preview`, **WE_MET_EXCHANGE_RATE_LIMITER** (namespace **2001**), and **WE_MET_FOLLOWUP_EMAIL_QUEUE** (non-prod queue); they do **not** receive **WORKER_SELF_REFERENCE** (production does). Details: [0019 § Proof deploy findings](../decisions/0019-pr-preview-github-action.md#proof-deploy-findings) (verified **2026-10-11**).

**D1 `database_id` values** in `wrangler.jsonc` are **placeholders** (real IDs stay out of the public repo). CI injects the real IDs from GitHub environment **secrets** at deploy time ([0020](../decisions/0020-d1-database-id-injection.md)).

**Non-prod D1 contents:** `we-met-db-nonprod` is not limited to synthetic test cards. Diadem’s real card (`slug` `didi`) is loaded there so PR previews show the live card. Step 1 safety relies on that card having **zero enabled lead sinks** and on the non-prod consumer’s hardwired mail redirect — not on the database holding only test data. **Never** add a sink row that points at a real destination to any card in non-prod D1.

## Deploy-time guards

`scripts/check-deploy-guards.mjs` (CI and `npm run deploy:guards`) **must fail** if:

- **Any entry** in `previews` `d1_databases`, `r2_buckets`, `queues.producers`, or `ratelimits` uses a **production** resource name or marker string.
- `previews.vars.WE_MET_ENV` is not `preview`, or top-level `WE_MET_ENV` is not `production` when checking production.
- Top-level production bindings (D1, R2, queue, rate limiter) do not match production resource names.
- Preview and top-level `database_id` values are identical (including after CI substitution).
- Production `routes` includes custom domain **`app.we-met.link`**; the `previews` block must not define that route.
- `config/nonprod-mail-safety.json` is missing, invalid, or does not **fail closed** when `WE_MET_TEST_MAIL_TO` is unset (spec mirrored by the non-prod consumer Worker in [DIDI-577](https://linear.app/didi-build/issue/DIDI-577)).
- Each top-level **D1** and **R2** binding has a **previews** counterpart with the **same binding name** and a resource name of `<production-name>-nonprod` (and the reverse).
- **Staging (`we-met-staging`):** when `wrangler` config for staging exists, guards for the **staging** deploy target must fail if any binding uses a production resource name (`we-met-db`, `we-met-assets`, production queue, or production rate-limiter ids), if `WE_MET_ENV` is not `staging`, or if the config references Worker **`we-met`** instead of **`we-met-staging`**. Staging deploy workflows must never invoke `wrangler d1 migrations apply` against **`we-met-db`**.

**Provision (CI):** `scripts/provision-resources.mjs` (Cloudflare REST API) creates missing D1/R2 resources on **production** deploy and in **`migrate-nonprod`** (`main` checkout only). **Preview does not provision.** D1 ids flow through gitignored `provision-d1-ids.json` and are never logged ([0020 amendment](../decisions/0020-d1-database-id-injection.md#amendment-2026-10-23-didi-683-create-if-missing-d1r2-and-env-validation), [deploy runbook](../runbooks/deploy.md#add-a-d1-database-or-r2-bucket-pr-only)).

Production deploys use the GitHub **`production`** environment (required reviewers); that gate is enforced by workflow structure tests, not by this script.

**Consumer mail safety:** redirect and fail-closed behavior use the consumer’s own `vars.WE_MET_ENV` and the secret `WE_MET_TEST_MAIL_TO` (non-prod only). Queue fields such as `lead.environment` are ignored for recipient selection.

**Consumer queue handling:** processes **`visitor_followup`** (immediate visitor letter after details finalize), **`visitor_letter_due`** (delayed visitor letter fallback after exchange), and **`email`** sink messages (`lead_sink_record`, `lead_sink_append_details`, `lead_sink_owner_email`, `owner_email_due`). Unknown `type` or unsupported `sinkKind` **retry** on the same schedule until Cloudflare discards them at `max_retries`. Malformed visitor letter or known sink bodies are logged and **acked** (sink failures best-effort mark ledger `failed`). Send failures retry with exponential backoff: delay after failed attempt _n_ (1-based) is **min(1800, 30 × 2^(n−1))** seconds. **`max_retries`** and the code attempt limit are **30**; worst-case delay before the final attempt is **43,290 s** (~12 h). After the 30th failed attempt the consumer logs a permanent failure (`leadId` and `sinkId` for sinks; `errorCode` only) and **acks**. Without a dead-letter queue, messages that reach the retry limit are **deleted** ([Cloudflare dead-letter queues](https://developers.cloudflare.com/queues/configuration/dead-letter-queues/)).

## Staging deploy access

Deploys to **staging** use GitHub environment **`staging`**: **no required reviewers**, **deployment branches `main` only**. Every push to `main` runs the staging deploy workflow ([0028](../decisions/0028-staging-we-met-didi-build.md), [deploy runbook](../runbooks/deploy.md)). Staging does not replace or bypass the production gate.

## Production deploy access

Deploys to **production** require the GitHub **`production` environment**, which uses required reviewers (Diadem approves production releases). A merge to `main` starts the deploy workflow; the job waits until an authorized approver approves. Only people granted **approval** on that environment can release to production. **Production approval is unchanged** by staging.
